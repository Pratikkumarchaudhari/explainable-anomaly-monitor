Explainable Data Anomaly Detection

Can an unsupervised model identify unusual data-processing behavior, and does it improve on simple rules? Inspect the evidence, including missed anomalies and false alarms, before deciding how to monitor a data pipeline.

This is a reproducible Python benchmark with an interactive results snapshot. It is not connected to live systems. All inputs are generated synthetic data; no bank, customer, or employer records are used.

01 / Business question

Prioritize unusual processing behavior for human review

A data steward might investigate sudden increases in errors, missing fields, response time, or record volume. This project demonstrates that workflow with simulated monitoring observations. Its goal is to evaluate detection quality and review workload while giving reviewers enough context to investigate each alert.

One row represents a simulated monitoring observation for a processing period. There are no actual dates, institution IDs, transaction amounts, or customer identities. Rows are independent draws; the project does not model a time series or prove fraud detection.

03 / Analysis platform and decisions

Python analysis, browser inspection

NumPy generates data; pandas validates and summarizes it; scikit-learn fits and evaluates Isolation Forest (200 trees, random_state 42). Local CSV/JSON files store inputs and outputs. HTML and JavaScript power this free browser report. There is no database, paid API, Snowflake, or Tableau connection in this project.

  1. Validate four numeric features: finite values, nonnegative volume/latency, rates within [0,1].
  2. Fit the model on training features only. Unusual records tend to be isolated in fewer random splits. No labels, IDs, scaling, or date features enter the model.
  3. Score normal calibration data using -model.score_samples(). The 98th percentile sets a fixed threshold of 0.5600186. Higher scores are more unusual; they are not probabilities.
  4. Score the held-out test set. A score ≥ threshold raises a model flag. Threshold selection does not use test labels.
  5. Compare fixed rules and a hybrid that flags a row when either the model or any rule flags it.
  6. Evaluate against injected labels and add training-relative deviation diagnostics for reviewers. No record is deleted or corrected automatically.

Model precision: 32 correct alerts / 50 alerts = 64%. Model recall: 32 found / 48 injected = 66.67%. TP = detected injected anomaly; FP = normal row flagged; FN = missed injected anomaly; TN = unflagged normal row.

The calibration false-positive rate is 2% (8 / 400); the held-out model false-positive rate is 3.26% (18 / 552 normal rows). Calibration is a target, not a guarantee. Average precision is 0.7468, a ranking metric across thresholds; it is different from the 64% precision at the chosen threshold.

Feature-level mean-shift diagnostics

Absolute(test mean − training mean) / training population standard deviation: volume 0.3432; error rate 0.3972; latency 0.1809; missing rate 1.1183. Missing rate has the largest standardized shift here. These are descriptive diagnostics influenced by injected anomalies, not significance tests or proof of production drift.

06 / Conclusion and next steps

Simple rules are the strongest baseline on this dataset

Rules catch every deliberately obvious injected anomaly without false alarms in this single benchmark. The model misses 16 and adds 18 false alarms. Hybrid recovers those 16 misses but keeps the 18 false alarms. Adding the model therefore does not improve on rules here.

The project demonstrates disciplined evaluation, threshold calibration, baseline comparison, and transparent human review. It does not establish real-world detection performance. Before using this approach operationally, test subtle multivariate anomalies and multiple seeds, add time-aware data and review labels, account for seasonality, and choose thresholds using investigation costs and reviewer capacity.
